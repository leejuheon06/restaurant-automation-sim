# 서빙 팔 자세를 AMR 상태에 연동하는 코드 수정 기획 (2026-11-26)

작성: 기획 패널. 코드 수정과 검증은 부장(Opus 5.5)이 맡습니다. **이 문서는 기획이며 실행하지 않았습니다.** 사용자가 실행을 지시하면 작업 지시서로 나눠 보냅니다.

- 관련: [2차 연동테스트 기획](2026-11-26_INTEGRATION_TEST_2_PLAN.md) 2.3절(요구 사항, A 항목), [접은 자세 측정](2026-11-20_SERVING_ARM_REST_POSE.md)
- 범위 밖: OPEN·CLOSE(서보 ON/OFF)는 이번에 하지 않습니다(사용자 결정, 2026-11-26).

> **이름 통일(사용자 결정, 2026-11-26 저녁):** 사용자에게 "home 자세"는 0도 자세다. 그래서 0도로 가는 작업 이름을 `HOME`, 접은 자세로 가는 작업 이름을 `REST`로 한다. 아래 본문의 `ZERO`는 `HOME`으로, "`HOME`(rest로 감)"은 `REST`로 읽는다. 설정 키도 `zero` 대신 `home`. 11-20에 넣은 `HOME`(= rest로 감)의 뜻이 바뀌는 것이다.

## 1. 요구 사항 (사용자 확정, 2026-11-26)

| AMR 상태 | 팔 자세 |
| --- | --- |
| 충전소에서 대기 | 0도 자세 `[0, 0, 0, 0, 0, 0]` |
| 임무를 위해 이동 중(손님 안내, 음식 가지러 가기, 식기 회수, 테이블로 서빙 이동. 운반 여부와 무관) | rest `[0, 122, -148, 143, 0, 60]`, 그리퍼 닫음 |
| 음식을 AMR로 옮기기 직전, 테이블에서 서빙하기 직전 | rest → 0도 자세로 한 번 간 뒤 동작 시작 |
| 팔 동작이 끝난 뒤 다음 이동 전 | rest로 접음 |
| 충전소에 돌아온 뒤 | 0도 자세로 폄 |

한 번의 서빙으로 쓰면: 충전소 대기(0도) → rest로 접음 → 조리대로 이동(rest) → 0도 → LOAD 동작 → rest → 테이블로 이동(rest) → 0도 → UNLOAD 동작 → rest → 충전소로 이동(rest) → 0도.

## 3. 설계

### 3.1 누가 접고 펴는가: 로봇 제어기(`mobile_controller`)가 스스로

| 방안 | 내용 | 판단 |
| --- | --- | --- |
| 가. 로봇 제어기가 출발·도착 때 스스로 | 경로를 시작하기 전에 팔이 rest인지 보고 아니면 접음. 자기 충전소에 도착해 서 있으면 0도로 폄 | **제안** |
| 나. 관제가 팔 작업으로 넣음 | 임무 단계마다 접기·펴기 작업을 끼워 넣음 | 관리자 이동 명령, 양보 후진, 홈 복귀, 재계획 경로 등 임무 밖의 이동마다 따로 넣어야 해서 빠지는 길이 생김 |

"어떤 이동이든 rest"는 이동이 실제로 시작되는 곳에서 막아야 빠지는 길이 없습니다. 모든 이동은 `mobile_controller._navigate` 하나를 지나므로 여기서 확인합니다. 관제와 인터페이스 정의의 필드는 바꾸지 않습니다.

### 3.2 팔 구동부 (`serving_arm_driver.py`, `serving_arm.yaml`)

1. 새 작업 이름 `ZERO`: 0도 자세로 감. `HOME`(rest로 감)은 그대로.
2. 작업 자세 목록을 **0도 → 작업 자세들 → rest**로 만듦. 지금은 "작업 자세들 → rest".
   - `HOME`은 rest 하나, `ZERO`는 0도 하나.
   - 자세가 비어 있는 작업(`COLLECT_DISHES`, `RETURN_DISHES`)은 지금처럼 `NO_POSE`로 실패하고 팔을 움직이지 않음.
3. 이미 목표 자세에 있으면 명령을 보내지 않고 바로 성공. jetcobot1에서 `send_angles` 한 번이 약 1.6초 걸렸으므로(11-20 측정), 이미 rest일 때 `HOME`이 지연 없이 끝나야 함.
4. `serving_arm.yaml`에 `zero: [0, 0, 0, 0, 0, 0]`을 두고 주석을 실제 동작에 맞춤. 0도로 갈 때 그리퍼는 건드리지 않음(rest로 갈 때만 닫음, 지금과 같음).
5. 실패·취소·시간 초과 때는 지금처럼 그 자리에 섬(rest로 보내지 않음). 다음 이동 전에 로봇 제어기가 접음(3.3).

### 3.3 로봇 제어기 (`mobile_controller.py`, `serving_arm:=real`일 때만)

1. **팔 자세 표시 `arm_pose`**: `ZERO` / `REST` / `UNKNOWN`. 기동 때 `ZERO`(충전소 대기 조건). 팔 구동부의 작업 결과로만 갱신:
   - `HOME` 성공, 그 밖의 작업 성공 → `REST`
   - `ZERO` 성공 → `ZERO`
   - 작업 시작, 실패·취소·비상 정지·구동부 끊김 → `UNKNOWN`
2. **출발 전 접기**: `_navigate`가 경로를 받아 첫 구간을 움직이기 전에 `arm_pose`가 `REST`가 아니면 팔 구동부에 `HOME`을 보내고 끝날 때까지 기다림. 그동안 로봇 상태는 새 값 `ARM_FOLD`로 보고. `REST`이면 아무것도 보내지 않으므로 재계획으로 경로가 자주 바뀌어도 지연이 없음.
3. **접기에 실패하면 출발하지 않음**: 구동부가 없거나(`ARM_OFFLINE`) 시간 초과(`ARM_TIMEOUT`)면 경로를 그 사유로 실패 처리. 관제는 지금의 팔 작업 실패와 같은 길로 임무를 보류(`SUSPENDED`)하고 알람을 냄. 비상 정지나 관제의 취소가 오면 접기도 취소.
4. **충전소 도착 뒤 펴기**: 경로가 자기 홈 노드(`roadmap.json`의 `homes`, 지금 지도는 H1~H3)에서 성공으로 끝나고, 새 경로 없이 1초(`arm_zero_delay`) 서 있으면 `ZERO`를 보냄. 펴는 중에 새 경로가 오면 2번이 다시 접음.
5. 팔 작업 중에는 경로를 시작하지 않음(지금도 관제가 순서를 지키지만 로봇 쪽에서도 거절).
6. 대역(`serving_arm` 없음, 시뮬 기본값)은 실제 팔이 없으므로 동작을 바꾸지 않음. RViz에 보이는 대역 자세를 요구 사항대로 바꿀지는 선택 사항(이번 범위에서는 하지 않음).

### 3.4 관제·인터페이스

- `fleet_core`: 바꾸지 않음. 접기 실패로 경로가 돌아올 때의 사유(`ARM_OFFLINE`, `ARM_TIMEOUT`)가 지금의 실패 처리(재시도 없이 보류)로 들어가는지만 확인하고, 아니면 그 분기만 추가.
- `ArmJob.action`: 필드는 그대로. 주석의 job 목록에 `ZERO`, `NavigateRoute.action` 주석의 reason 목록에 `ARM_OFFLINE`·`ARM_TIMEOUT` 추가. `RobotStatus.msg` 주석의 state 목록에 `ARM_FOLD` 추가.
- Confluence I/F v0.3: 28번의 `job`은 값 목록이 없어 새 값이 정의서와 어긋나지 않음(코드에 더 있는 것). 24번 경로 결과의 사유 값과 33번 상태 값도 정의서에 목록이 없음. 작성자에게 "값이 늘었다"고 알려 줄 항목으로 남김.

### 3.5 시간에 미치는 영향 (계산값, 실측 아님)

- 0도 ↔ rest 한 번이 속도 60에서 약 2.1~2.4초(11-20 측정). 서빙 한 건에 접고 펴기가 6번(출발, LOAD 앞뒤, UNLOAD 앞뒤, 충전소 도착) 들어가 약 13~15초가 붙음. 이 가운데 4번은 지금도 하고 있거나(작업 뒤 rest) 작업 안에 있음.
- 1차 서빙 소요 67.7~86.5초와 직접 비교하면 늘어남. 관제의 계획 시간(팔 작업 3초)은 실제와 더 벌어짐(기존 문제, 이번에 바꾸지 않음).
