## 1. 왜 이 시험을 하는가

- **1차에서 남긴 것을 닫기 위해서.** 1차는 서빙 4건, 자동 복귀, 2대 회피 6단계, ESTOP을 통과했지만 T-07(도킹 중 벽 접촉)과 T-08(자동 위치 추정)은 실패였고, B-04~B-07 네 건은 "수정해서 배포했지만 실기기에서 확인하지 못함"으로 남았습니다. 같은 시나리오를 다시 돌려야 이 네 건의 상태를 바꿀 수 있습니다.
- **1차 뒤에 바뀐 것이 같은 시나리오를 깨지 않는지 보기 위해서.** 1차 뒤에 서빙 팔 대기 자세(11-20), 천장 카메라 위치 판정(T-55·T-57), 바퀴 치수 보정(T-58·T-60), `cmd_vel` 감시 0.3초, 통신 감시 2초 → 1초, 인터페이스 이름 변경(11-25)이 들어갔습니다. 인터페이스 이름 변경은 빌드와 경량 시뮬만 통과한 상태입니다.
- **지금 지도로는 판정을 할 수 없어서.** 매장 배치가 지도와 달라 위치 추정이 밀리는 상태(T-61)에서 도킹 오차, 로봇 간 거리, 위치 추정 항목을 재면 지도 탓인지 코드 탓인지 가를 수 없습니다. 그래서 지도 준비를 시험 앞에 둡니다.
- **팔을 AMR에 올린 운용 절차를 처음 확인하기 위해서.** 주행 중 팔이 접혀 있는지, 영업 시작·종료 때 서보를 켜고 끄는 것이 안전하게 되는지는 1차에 없던 항목입니다.

위 이유는 기획 초안입니다. 문서에 남길 타당성 문장은 사용자와 함께 다듬습니다.

### 2.3 서빙 팔 추가 항목 (A)

**요구 사항(사용자, 2026-11-26 확정):** 서빙 팔 자세는 AMR 상태에 따라 아래와 같아야 한다.

| AMR 상태 | 팔 자세 |
| --- | --- |
| 충전소에서 대기 | `[0, 0, 0, 0, 0, 0]` |
| 임무를 위해 이동 중(손님 안내, 음식 가지러 가기, 식기 회수, 테이블로 서빙 이동 등, 운반 여부와 무관) | rest |
| 음식을 AMR로 옮기기 직전, 테이블에서 서빙하기 직전 | rest → `[0, 0, 0, 0, 0, 0]`으로 한 번 간 뒤 동작 시작 |

이에 따라 A-03은 셋으로 판정한다: P1 이동한 모든 구간에서 rest가 아닌 시간 0초, P2 충전소 대기 중 0도 자세가 아닌 시간 0초, P3 팔 작업마다 0도 자세를 거친 뒤 시작. 지금 코드와의 차이(코드 읽기 기준, 시뮬로 확인 중): ① 출발 전에 rest로 접는 동작이 없음 ② 충전소에 도착해도 0도로 펴지 않음(작업이 성공하면 rest로 끝남) ③ 작업 자세는 rest에서 바로 시작하고 0도를 먼저 거치지 않음 ④ 작업이 실패·취소되거나 비상 정지가 오면 그 자세로 남음. OPEN·CLOSE(서보 ON/OFF)는 이번 확인 범위에서 뺀다(사용자, 같은 날). 처음 받은 요구("출발 전 0도, 물건을 옮기는 중이 아닌 이동에서는 rest")는 이 표로 대체한다.

## 4. 시험 전 준비 작업 (부장 지시 예정, 결정 뒤 작업 지시서로 나눔)

### 4.1 서빙 팔 OPEN·CLOSE (코드 변경)

지금 동작(`serving_arm_driver.py`): 기동 때 서보를 건드리지 않고 자동으로 접지도 않음. 작업을 시작할 때 `power_on()`. 취소·시간 초과 때 `stop()`(전원 유지). 종료 때 서보를 끄지 않음.

바꿀 것(제안, 결정 1~3에 따라 달라짐):

- `OPEN`: 서보 ON → 대기 자세로 이동(그리퍼 먼저 닫음) → `OK`
- `CLOSE`: 대기 자세로 이동 → 도착 확인 → 서보 OFF → `OK`. 대기 자세에 닿지 못하면 서보를 끄지 않고 실패를 돌려줌
- 서보가 꺼진 상태를 구동부가 기억하고, 그 상태에서 온 작업은 결정 3대로 처리
- 구동부 종료(SIGINT·SIGTERM) 때 서보를 어떻게 둘지 정함. 바퀴 모터는 스택을 꺼도 토크가 남는 문제가 있었음(T-59)
- pymycobot 3.9.2에서 서보를 끄는 호출(`power_off`, `release_all_servos` 중 무엇을 쓸지)과 켜짐 조회는 부장이 팔 Pi의 설치본에서 확인(기획은 확인하지 않음)
- 문서: `serving_arm.yaml` 주석, `ArmJob.action`의 job·reason 목록, `src/frybot/README.md` 서빙 팔 절, `COMMANDS.md` 서빙 팔 시험

완료 기준: 가짜 팔 단위 시험(OPEN·CLOSE·꺼진 상태 작업·대기 자세 실패 때 CLOSE), 경량 시뮬 `serving_arm:=real` 가짜 서버로 SERVE 1건, 팔 Pi 배포와 md5 일치. 실물은 5장 단계 2에서 확인.

### 5.1 명령 (최종 v0.3 이름 기준, `<새 지도>`와 노드 이름은 결정 뒤 채움)

```bash
# 팔 Pi 에서 칠 한 줄 출력 → 팔 Pi 에서 실행
python3 -m frybot_bringup.robot_remote jetcobot1 --arm-command --mount pinky1
# 로봇 기동(초기 자세 없음)
python3 -m frybot_bringup.robot_remote pinky1 --map-id <새 지도>
python3 -m frybot_bringup.robot_remote pinky2 --map-id <새 지도>
# 관제
ros2 launch frybot_bringup real.launch.py map_id:=<새 지도> robots:=pinky1,pinky2 \
  remote:=false serving_robots:=pinky1 run_id:=<YYYYMMDD_NN_이름>
# 팔 단독
ros2 action send_goal /pinky1/arm_job frybot_interfaces/action/ArmJob \
  "{task_id: 'a01', arm_id: 'pinky1', job: 'REST', duration: 3.0, params_json: '{}'}"   # REST = 접은 자세, HOME = 0도 자세
# 서빙
ros2 service call /fms/submit_task frybot_interfaces/srv/SubmitTask \
  "{task_type: 'SERVE', table_id: 1, menu: 'FRIED'}"
# 관리자 명령
ros2 service call /frybot/admin frybot_interfaces/srv/AdminCommand \
  "{command: 'MOVE_TO_VERTEX', target: 'pinky1', arg: '<노드>'}"
```

`OPEN`·`CLOSE`는 4.1이 끝난 뒤 같은 `send_goal` 형식에 `job`만 바꿔 보냅니다(결정 2가 제안대로일 때). 서빙과 관리자 명령은 최종 v0.3 이름(`/fms/submit_task`, `/frybot/admin`·`AdminCommand`)으로 적었습니다. 지금 코드는 아직 11-25 이름(`/frybot/tasks/submit`, `/frybot/central/request_admin_operation`·`RequestAdminOperation`)이고, 이름을 되돌리는 작업이 끝나야 위 명령이 그대로 통합니다(4.4절). 필드는 두 이름에서 같으며 소스 정의, 관제 PC 설치 빌드(`ros2 interface show`), 노드 코드와 대조했습니다. `mobile_controller`는 `serving_arm:=real`일 때 받은 목표를 고치지 않고 팔 구동부로 넘기므로, 새 작업 이름 `OPEN`·`CLOSE`는 인터페이스 정의와 `mobile_controller`를 바꾸지 않아도 전달됩니다. 로봇 세 대와 팔 Pi에 배포된 빌드는 확인하지 않았습니다(단계 0에서 확인).
