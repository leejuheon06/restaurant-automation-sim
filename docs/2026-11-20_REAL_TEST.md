## 문서 연결과 해석 범위

- 1~5절은 2026-11-20 당시 실행한 명령·측정·시나리오 이력이고, 6절은 미실행 계획입니다. 반복된 명령도 실행 맥락을 보존하기 위해 유지합니다. 현재 사용법과 시험 초안은 [COMMANDS](COMMANDS.md), 원인·수정·검증 상태는 [TROUBLESHOOTING의 T-42~T-52](TROUBLESHOOTING.md)을 참고합니다. 당시 명령과 현재 권장 명령이 다를 수 있습니다.
- 전날의 기동·RViz·지도 노드 수 비교는 [2026-11-19 실기기 기록](2026-11-19_REAL_TEST.md)에 있습니다. 전날 지도 비교의 종료 결정과 오늘 서빙·2대 시험은 별도 실험입니다.

## 2. 공통 명령

모든 명령은 관제 PC의 `~/frybot_ws`에서 `source install/setup.bash` 뒤에 실행했습니다. `scripts/stop_all.sh`는 다른 작업의 시뮬과 `robot_remote`까지 끄므로 쓰지 않았습니다.

### 2.1 배포·점검

```bash
python3 -m frybot_bringup.robot_remote pinky1 --deploy      # pinky2, pinky3 도 같은 형식. 수정이 올 때마다 세 대에 실행
python3 -m frybot_bringup.robot_remote pinky2 --check
python3 -m frybot_bringup.robot_remote pinky1 --map-id test_map_v05 --dry-run   # 기동 명령 미리 보기
```

`ros2 run frybot_bringup robot_remote ...` 형식은 `stop_all.sh`의 `lib/frybot` 패턴에 걸려 죽은 적이 있어 `python3 -m` 형식을 썼습니다.

### 2.2 팔 구동 노드 (팔 Pi)

```bash
python3 -m frybot_bringup.robot_remote jetcobot1 --arm-command --mount pinky1   # 팔 Pi 에서 칠 한 줄 출력
# 출력된 줄을 팔 Pi(ssh jetcobot@192.168.0.37)에서 실행:
source /opt/ros/jazzy/setup.bash ; source ~/frybot_robot_ws/install/setup.bash ; export ROS_DOMAIN_ID=73 ; \
  export ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST ; export ROS_STATIC_PEERS='192.168.0.9;192.168.0.20' ; \
  setsid -f nohup ros2 launch frybot_mobile serving_arm.launch.py robot_id:=pinky1 \
  'python:=~/venv/jetcobot/bin/python3' port:=/dev/ttyJETCOBOT > ~/.frybot/serving_arm.log 2>&1 < /dev/null
pkill -TERM -f 'frybot_mobile.[s]erving_arm_driver'        # 종료
```

## 4. 2대 시나리오 (09)

| 단계 | 준비 이동 | 시험 명령 | 결과 |
| --- | --- | --- | --- |
| 0 정렬 | pinky1 W1 → B1 → W1 | — | 노드에서 1.8 cm |

## 5. 남은 것

- 자동 위치 추정의 홈 근처 우선(T-51)은 배포만 했고 실기기 기동에서 확인하지 않음
- 위치 추정 감시·보정(T-50)은 09 에서 한 번도 발동하지 않아 실기기 동작을 확인하지 못함
- 노드 밖 판정 기준(6 cm), pinky1 이동 명령 거절 원인, pinky2 의 B2 → B1 구간 Nav2 실패는 후속 작업
- pinky1 배터리 27 %(관제 하한 25 %)에서 종료
- 노드 밖 점유 기준 12 cm 와 같은 노드로 다시 세우는 명령(T-52)은 09 뒤에 세 대(pinky1·2·3)에 배포만 했고 실기기에서 확인하지 않음. 위 "노드 밖 판정 기준(6 cm)"과 "이동 명령 거절 원인"의 후속 수정이 이것임(거절 사유는 `MOVE_REJECT` 이벤트로 남음)
- pinky1 상태 보고가 1~3초씩 끊기는 원인(네트워크 또는 Pi CPU)은 확인하지 않음

## 6. 다음 시험 시작 순서 (2026-11-21 예정)

09 종료 시점에 세 대의 로봇 코드는 PC 와 같고(T-52 까지 배포), 켜져 있는 frybot 프로세스는 없습니다. 아래는 계획이며 실행한 기록이 아닙니다.

준비(사람이 할 일):

- pinky1 을 충전한 뒤 W1 에, pinky2 를 W2 에 +y 방향으로 놓음
- jetcobot1 팔 Pi 전원 확인(2026-11-20 12:30 무렵 전원이 한 번 끊겨 재부팅됨)
- 지도는 `test_map_v05` 그대로. 노드를 바꾸면 시험 전에 다시 배포
- 등록부 `~/.config/frybot/robots.yaml` 의 jetcobot1 `mount` 는 `[pinky1]`(pinky2 는 팔 없음)

기동(명령은 2.2, 2.3, 2.6 과 같음):

1. 팔 구동 노드: `python3 -m frybot_bringup.robot_remote jetcobot1 --arm-command` 가 출력한 줄을 팔 Pi 에서 실행
2. 로봇: `python3 -m frybot_bringup.robot_remote pinky1 --map-id test_map_v05`, pinky2 도 같게. **초기 자세를 주지 않음**
3. 관제: `real.launch.py map_id:=test_map_v05 robots:=pinky1,pinky2 remote:=false serving_robots:=pinky1 run_id:=20261121_01_<이름>`
4. 카메라와 관제 화면 녹화 시작, 끝나면 `merge_videos.py` 로 합침

먼저 확인할 것(순서대로):

| 번호 | 확인 | 통과 기준 |
| --- | --- | --- |
| 1 | 자동 위치 추정(T-51) | 로봇 로그에 `auto localisation OK`·`OK_HOME`·`OK_SAVED` 중 하나가 나오고 `/initialpose` 를 손으로 넣지 않아도 상태가 IDLE 이 됨. `AMBIGUOUS`·`NOT_LOCALIZED` 면 실패 |
| 2 | 노드 밖 점유와 다시 세우기(T-52) | 노드에서 벗어난 로봇 12 cm 안의 노드로 가는 명령이 막히고, 벗어난 로봇을 같은 노드로 `MOVE_TO_VERTEX` 하면 받아서 다시 섬. 거절되면 `MOVE_REJECT` 에 사유가 남음 |
| 3 | 위치 추정 감시·보정(T-50) | 로봇 로그에 60초마다 `pose monitor: checks N, last score S, corrections K` 가 나옴. 보정이 일어나면 `pose corrected` |

계획 판정 보충(현재 구현과의 대조):

- 1번에서 `OK`·`OK_SAVED`로 기동하면 자동 위치 추정은 확인되지만, T-51의 홈 후보 fallback까지 확인한 것은 아닙니다. 저장 자세 후보가 맞지 않는 조건에서 `OK_HOME`이 나오는지 별도로 구분해 기록합니다.
- 2번의 12 cm는 서 있는 로봇의 **보고 위치와 목표 노드 사이 거리**입니다. 명령 접수 자체가 거절되는 경우와 접수 후 계획·허가가 막히는 경우를 구분합니다. 경로를 계획할 수 없는 상태가 20초 넘게 이어지면 `PLAN_FAIL`로 보류됩니다. 같은 노드 재정렬은 1.5 cm 초과 오차와 이동 가능 상태가 전제이며, `MOVE_REJECT`는 이동 가능 상태 검사에서만 기록됩니다. 이미 도착한 노드·출발 노드 점유 등의 거절은 반환 메시지를 함께 확인합니다.
- 3번의 주기 요약은 감시 실행 여부를 확인하는 기준입니다. `checks` 증가와 점수를 확인하되, `corrections=0`이면 보정 동작의 실기기 검증은 계속 미확인으로 남깁니다.
- 위 기동 3번은 인자 요약입니다. 2.3절처럼 ROS 도메인·탐색 상대를 설정한 관제 PC에서 `ros2 launch frybot_bringup real.launch.py` 뒤에 해당 인자를 붙입니다. `<이름>`은 실제 이름으로 바꿉니다. 배포 상태와 프로세스 종료 여부도 다음 시험 직전에 다시 점검합니다.

그다음 4 장의 2대 시나리오 6단계를 다시 돌려 09(임무 21건, RETREAT 4, PLAN_WAIT 6, REPLAN 9, ROUTE_RETRY 2, ROUTE_FAIL 0, 최소 중심 거리 14.5 cm)와 비교합니다.

정하지 않은 것: AMCL 파라미터와 최대 회전 속도 변경 제안의 적용 여부, 주행 중 팔 자세, v05 통로 보완(A4–B4), 로봇 홈 폴더의 옛 지도 파일 삭제.
