실측 지도 `test_map_v001`, `test_map_v002`의 대기 위치와 로봇 출발 노드를 맞춘 기록입니다. 바뀐 파일은 `src/frybot/frybot_control/frybot_control/maps/`의 두 `roadmap.json`뿐이고, 코드는 고치지 않았습니다.

> 아래 배포·검증 상태는 17일 작성 당시 기준입니다. 이후 실기기 결과는 [18일 기록](2026-11-18_REAL_TEST.md)과 [19일 기록](2026-11-19_REAL_TEST.md), 현재 명령은 [COMMANDS.md](COMMANDS.md)를 참고하세요.

## 1. 바뀐 내용

| 파일 | 항목 | 이전 | 이후 |
|---|---|---|---|
| `test_map_v001/roadmap.json` | W2 좌표 | (1.26, -0.55) | (1.26, -0.575) |
| `test_map_v001/roadmap.json` | W3 좌표 | (1.99, -0.574) | (2.163, -0.58) |
| `test_map_v001/roadmap.json` | W3 통로 | B6–W3 | B7–W3 |
| `test_map_v001/roadmap.json` | `homes` | A2, W3, W1 | W1, W2, W3 |

- v001의 W1 (0.663, -0.58)은 이미 v002와 같아 그대로입니다.
- `homes`는 로봇 번호 순서입니다. 이제 두 지도 모두 pinky1 → W1, pinky2 → W2, pinky3 → W3입니다.
- **W3 통로를 바꾼 이유:** W3를 B7 (2.163, -0.419) 바로 아래로 옮기자 기존 B6–W3 통로가 대각선이 되어 B7에서 약 12.5 cm로 지나갔습니다. `SAFE_DIST`(15.5 cm)보다 가까워 v002와 같은 B7–W3로 바꿨습니다.
- JSON에는 주석을 달 수 없어 `[수정]` 표기는 파일에 넣지 못했습니다.

## 2. 확인

### 경량 시뮬

`ros2 launch frybot_bringup sim.launch.py map_id:=<지도> net:=local`로 띄우고, 관리자 API(`POST /api/admin`, `MOVE_TO_VERTEX`)로 이동시켰습니다.

| 지도 | 출발 위치 | 이동 |
|---|---|---|
| `test_map_v001` | pinky1 W1, pinky2 W2, pinky3 W3 | pinky3: W3→B7→B6→B5, 복귀 B5→B6→B7→W3 / pinky2: W2→B3→B3_B4→B4 왕복 |
| `test_map_v002` | pinky1 W1, pinky2 W2, pinky3 W3 | pinky3: W3→B7→B5 왕복 / pinky1: W1→B1→A1 왕복 |

- 이동 명령 8건 모두 `ok: true`로 도착했고, 끝난 뒤 세 로봇이 W1·W2·W3에 섰습니다.
- v001에서 W3 출입은 B7을 거칩니다. B6에서 W3로 바로 가는 경로는 나오지 않습니다.
- 경량 시뮬은 Nav2·라이다·AMCL을 거치지 않으므로, 실제 주행(특히 옮긴 W3 진입)은 실기기에서 따로 봐야 합니다.

### pinky1 배포 대조

- `ros2 run frybot_bringup robot_remote --all --deploy`: pinky1은 4개 패키지 복사와 빌드가 끝났습니다(`deploy finished`). pinky2·pinky3는 `could not reach the robot`.
- 로봇의 두 `roadmap.json` md5가 PC와 같습니다(v001 `b8f29f5b…`, v002 `ddcfa4d9…`).
- 로봇에서 지도를 불러와도 두 지도 모두 홈이 W1, W2, W3로 나옵니다.

## 3. 남은 일

1. pinky2·pinky3를 켠 뒤 배포: `ros2 run frybot_bringup robot_remote pinky2 pinky3 --deploy`
2. 실기기 확인: 세 로봇을 W1·W2·W3에 두고 기동, pinky3의 W3↔B7 출입 확인
3. v001에서 pinky1의 홈이 A2에서 W1로 바뀌었으므로, 기동할 때 로봇 위치나 `poses:=`를 그에 맞춤. README와 `real.launch.py`의 예시(`poses:=pinky1:A2,pinky3:W3`)는 그대로 둠

## 4. 왜 배포와 원격 기동 명령이 따로 있는가

관제 PC와 Pinky가 서로 다른 컴퓨터라서, 코드와 지도를 로봇마다 따로 갖고 있어야 하기 때문입니다.

- 경로와 통행 허가는 관제 PC가 정하지만, 실제 주행(Nav2, AMCL, 모터·라이다 드라이버, `mobile_controller`)은 각 Pinky의 라즈베리 파이에서 돕니다. 이 노드들은 로봇 쪽 사본의 `roadmap.json`과 지도 이미지를 읽습니다.
- PC에서 고친 것은 로봇에 자동으로 가지 않습니다. 지도가 서로 다르면 관제가 아는 좌표와 로봇이 가는 좌표가 어긋납니다. `--deploy`는 PC의 `src/frybot`을 로봇에 복사하고 로봇에서 빌드해 둘을 맞춥니다.
- `robot_remote`는 로봇마다 SSH로 들어가 복사·빌드·실행하던 일을 대신합니다. `real.launch.py`가 로봇마다 이것을 불러 PC에서 런치 한 번으로 전체가 뜹니다.
- 기동할 때 PC의 `ROS_DOMAIN_ID`를 로봇에 넘기고(로봇 3대의 `~/.bashrc` 값이 73·30·99로 다름), 이전 실행에서 남은 프로세스를 정리합니다.
- 배포는 코드나 지도를 바꿨을 때만 필요합니다. 시뮬레이션은 PC 안에서만 돌아 배포가 필요 없습니다.

## 5. 이 구조가 지연이나 오동작의 원인이 될 수 있는가

배포는 주행 중 수행하지 않으며, 주행 명령은 ROS로 전달됩니다. 이 사실만으로 원격 기동·로그 중계의 부하 영향을 배제할 수는 없습니다. 아래 내용은 17일 당시 가설이며 원인 확정이 아닙니다. 이후 CPU·송신량 실측은 [19일 C5·C6](2026-11-19_REAL_TEST.md)에 보존합니다.

**구조에서 확인한 부분**

- 배포는 코드가 바뀔 때 한 번 하는 복사·빌드이고, 주행 중에는 아무 일도 하지 않습니다.
- SSH는 로봇의 `robot.launch.py`를 시작시킬 뿐이고, 주행 중 통신은 ROS 토픽으로 직접 오갑니다.
- 무거운 경로 계획·배정은 PC가 하고 로봇은 허가받은 한 구간만 주행합니다. Nav2를 PC로 옮기면 라이다와 `cmd_vel`이 Wi-Fi를 타게 되어 지연과 끊김에 더 취약해집니다.

**걱정할 만한 부분**

- **Pi의 CPU 부하:** 로봇 한 대에서 AMCL, 전역·지역 costmap, planner, controller, 행동 트리, 도킹 서버, 라이다 드라이버, Python 노드가 함께 돕니다. CPU가 포화되면 제어 주기가 밀려 출발이 늦거나 주행이 끊길 수 있습니다.
- **이미 관측된 지연:** 11/16 실기기 로그에서 구간마다 약 2.27초의 고정 지연이 있었고 실제 소요가 예상의 1.76배였습니다(T-23). Pi 성능 때문인지 Nav2 목표 처리·도착 판정 때문인지는 가려지지 않았습니다.
- **Wi-Fi 의존:** 통행 허가와 생존 신호가 Wi-Fi로 갑니다. 끊기면 로봇이 멈추도록 되어 있어 위험하지는 않지만 멈칫거림으로 보일 수 있습니다.
- **SSH 세션:** [16일 수정 기록](2026-11-16_CHANGES.md)의 오후 수정에는 로봇 프로그램을 SSH와 분리해 실행하고 자동 재접속하도록 변경한 이력이 있습니다. 따라서 “분리 여부 미확인”이라는 당시 설명은 중복 조사 대상으로 두지 않습니다. 연결·중계 부하의 영향은 별도 확인 대상입니다.

**다음에 할 측정:** pinky1에 실기기 스택을 띄운 상태에서 CPU·메모리 사용률, 노드별 점유율, 제어 주기를 재면 Pi가 병목인지 알 수 있습니다.
